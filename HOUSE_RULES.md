Craftspace is this team's company brain: shared Pages, Playbooks, and decisions, reachable over MCP. Two standing rules. (1) READ FIRST: before acting on anything about how this company works — its people, product, decisions, process, or tools — consult the brain first, don't answer from assumptions it may already hold. If this repo has a local `brain/` folder (Brain as Code — see below), grep it directly: it is the same context on disk, zero setup, and current to the working tree. Otherwise, or to search across repos, use search_pages or list_pages, and the Playbooks listed here for a matching procedure, then read_page for the detail.

(2) WRITE BACK durable learnings, and only those: the moment you learn something that will still help a teammate next month — a decision and its why, a gotcha, a procedure that worked — save it. Skip the ephemeral: flaky or one-off transients, generic tooling knowledge, or another project's facts. Classify each by shape: a hard-to-reverse call is a Decision; a repeatable procedure is a Page under the Playbook it belongs to; a reusable gotcha or how-it-works fact goes under the Gotchas heading of the page for the feature it bites; a one-off dated status ('did X today', 'swapped Y on this date') with nothing procedural to teach is a single line in MEMORY, not its own entry. Search first and extend the matching entry instead of duplicating; if a session holds several learnings, capture the most important one fully. A learning left in your session is lost to the team.

Where each write LANDS depends on the repo. If this repo has a local `brain/` folder (Brain as Code), the repo is the source of truth, so WRITE A MARKDOWN FILE and do NOT use the MCP upsert tools: a file rides your normal PR and review, while an MCP write would push straight to `main` and skip that review. File it by kind under the base folder — a Decision in `brain/decisions/<slug>.md`, a Skill in `.agents/skills/<name>/SKILL.md`, a Page or MEMORY in `brain/<slug>.md`, where `<slug>` is lowercase with each run of non-alphanumerics collapsed to one `-`. Grep `brain/` first and EDIT the file that already covers the topic; the filename is the entry's identity, so a differently-named second file is a duplicate, not an update. A leading `--- … ---` frontmatter block of flat `key: value` lines carries metadata: a Decision takes `status: accepted` and a body of `# Title` then four `## ` sections — Decision, Context, Why, Consequences; a Skill takes `name:` and `description:` and a body of the procedure; a Page just takes a `# Title` heading. A Page is an **Area spine**: Title Case, an emoji icon, one line per term defining what that term IS, and any term that outgrows its line graduates to its own file beside the page. Be opinionated — one canonical word per concept, retired aliases on an `_Avoid_` line. A page backed by code ends in a `## Key files` list: directories rather than files wherever a directory covers it, never line numbers, and name the entry-point symbol when there is one. A gotcha is never its own page; it is a bullet under the `## Gotchas` heading of the page for the thing it bites. There is no spaceId to choose — the repo maps to one space, and the sync mirrors your file into the brain on merge. The folder tree in the app IS the folder tree on disk: `brain/area/index.md` is the page for `area`, and `brain/decisions/` is an ordinary folder with its own `index.md` holding the numbered decisions.

If there is NO local `brain/` folder, write over MCP instead: upsert_decision or upsert_page, and a one-off status as a line in the MEMORY page. Context then lives in spaces: a Shared space is a PROJECT — the org has one per project, each named after it, all org-wide readable and writable — plus the connected member's private Personal space. list_pages shows each space with its id and name; pass that spaceId on every upsert. With ONE Shared space there is no choice to make; with SEVERAL, write to the space whose name matches the project you are working in, and if none matches, ASK rather than defaulting into the first one — a second project's context does not belong in another project's space. Writes are live immediately with no in-app undo, so search before you create and extend an existing entry rather than adding a duplicate.

Keep every write short and human — a few tight sentences or a short list, never an essay; the brain is skimmed, not read. Organize a space into Areas — top-level pages (in a `brain/` repo, the wiki files) that fit what it holds, so an Engineering project grows different ones than a Sales one — plus a MEMORY page for quick dated notes that have not earned their own entry yet. File each learning in the Area it belongs to. When an Area is thin on context, run the grill-me skill to interview the team and capture that Area's language and decisions back into Craftspace.
